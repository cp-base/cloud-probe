作成・更新：2026-11-07。状態：**全体模型v0.2の土台を実装し、処理・UI・実画面を検査。次は全体の試遊と調整。**

ゲーム全体の範囲・仮案は[設計図](cloud-probe-blueprint.md)、ここまでの実測と会話は[調査履歴](cloud-probe-study-log.md)を参照。

## 1. この手順の目的

「毎回違う局所模型を作る」進め方から、一つの全体模型を継続して育てる進め方へ移る。

工程は実装を進める順番であり、途中の小さな部品だけをゲーム全体の代わりにするものではない。世界・発見・戦闘・成長・施設と活動・保存のつながりを、最初から同じ図の中で扱う。

この文書は今回の制作案。別プロジェクトの共通ルールとして設置するものではない。

## 4. P1で確認した参照元の差

- 旧模型は戦い方を選択式に分けていた。今回の本体では遠近自動切り替えへまとめた。
- 敵は1タイプ、強さは一定。4タイプの共存と深度の設定がまだない。
- 現模型の疎ら8対象/320区画、速度18は、多い・速いという試遊結果。新しい初期値の基準にしない。
- 回収数はあるが、資金・成長・施設・保存の循環はまだない。
- 表示は3D。純2Dに変更できるかの検証とは分ける。
- 既存の自動テスト13項目は、以前の模型のルールを確認したもの。変更後の検証結果として流用しない。

## 5. 設定と処理を増やす順番

1. 設計図のどの状態・経路を実現するのかを特定する。
2. 既存コード、Godot標準機能、取得済みサンプルで使える部分を確認する。
3. 共通の処理を作り、敵・武器・施設の違いは設定として渡す。
4. 設定の初期値と仮置き理由を残す。
5. 同じ設定を、表示・説明・ダメージ計算・テストが参照する。
6. 部品の確認後、探索から帰還・投資・次の探索までの経路へ接続する。

Resourceの共有データへ個体の現在耐久を直接書き込まない。生成時の設定と、保存されるプレイヤーの変更を区別する。

## 6. 検証を分けて記録する

| 確認方法 | 主な対象 | 言えること |
|---|---|---|
| インポート・構文確認 | スクリプト・リソース・シーン | 読み込めること。見えることや面白さは別 |
| 処理の自動テスト | 生成、攻撃、取引、保存など | 設定した条件で状態が正しく変わること |
| 再現操作 | 出発・回収・帰還・強化などの一連 | 複数分野の接続と、同じ入力の再現性 |
| 実画面操作 | ボタン、表示、対象の視認性、画面間の遷移 | 実際の画面で操作して結果が返ること |
| 通常試遊 | 初期の弱さ、移動の長さ、危険、成長 | 実際に感じた範囲。全域の保証にはしない |
| 境界・負荷確認 | 10000付近、区画境界、長時間、対象数 | 実行した条件の限界と負荷 |

検証用に座標・資金・能力を与えた場合は明記する。正常終了やログだけで画面の目的物が見えたと判断しない。以前の一人称デモでの表示確認の誤りを繰り返さない。

### 横断して確認する経路

- 発見した光の成果で改修し、同じ進路を再探索する。
- 強化前には負けた敵を、同じ深度・同じタイプで強化後に再度試す。
- 施設候補地を発見して建設し、終了・再開後に利用する。
- 登録施設から出発しても、世界の深度が変わらないことを確かめる。
- 交易で得た資金を別の投資へ使う。
- 調査派遣で得た地点情報を、次の航行で利用する。
- 燃料切れ・耐久切れから、成果保持と再出撃へつながる。
- 保存・再開後に、光の二重回収、二重建設、二重受領が起こらない。

### 2026-11-07 / P1〜P7：全体模型の土台を作成

**ユーザーの判断**：「いまから作るのが一応土台」「使える部分は使っていいけど無理にそっちに寄せるのはやめよう」。これを受け、既存模型を必ず拡張するという記述を訂正した。

**実施した順番**

1. 旧模型の描画・処理と全体設計の差を確認し、光と床のシェーダーを再利用対象とした。
2. `godot-foundation`に継続用の本体を作成。恒久状態Campaign、生成World、操作・進行Session、保存Storageに分け、表示とUIから同じSessionを参照した。
3. 敵4種・武器4種をGodotのResourceとして作成。個体の位置・耐久・待ち時間を共有Resourceとは別にした。
4. 固定施設と出撃ごとの光・信号・敵を分離。速度6、480区画あたり最大1対象、一般生成の最低間隔150へ減らした。
5. 航行・燃料・回収・地理的深度・遠近自動攻撃・投射物・帰還をつなぎ、成果→改修→再出撃を追加した。
6. 施設の機能を分け、建設と出発登録、固定装備、交易1品、調査派遣1枠、地点メモを接続した。
7. 保存版と生成版を設け、現在の探索も保存。一時ファイルを読み返してから置き換え、直前のファイルを`.bak`に保持する方式にした。
8. 施設5タブ・地図・HUD・一時停止・設定をGodot標準のControl/Containerで構成。追加発光は初期OFFとした。
9. headlessの処理検査、実シーンのUI検査、実ウィンドウの操作を分けて行い、問題を修正した。
10. 初期航行から帰還・改修・再起動まで確認し、進行を保存しない検査用配置で敵4タイプと自動砲撃の描画を確認した。
11. 設計図の再利用方針と現在の仮値を更新し、案内・検証記録・起動ファイル・ソースZIPを用意した。

**実行したコマンドの形**

検査に使ったGodotは4.7.2。実行ファイルは各PCのGodotの場所を指定する。
`<本体>`は `<リポジトリ>/godot-foundation`。

```text
Godot --headless --editor --path <本体> --import --quit --log-file <ログ>
Godot --headless --path <本体> --script res://tests/test_session.gd --log-file <ログ>
Godot --headless --path <本体> --script res://tests/test_ui.gd --log-file <ログ>
Godot --path <本体> --audio-driver Dummy --log-file <ログ>
Godot --path <本体> --script res://tests/visual_fixture.gd --audio-driver Dummy --log-file <ログ>
```

ここではコマンドの形を残している。通常の起動にコマンドを覚える必要はなく、[共有版の起動案内](cloud-probe-prototype-guide.md)を使える。

**問題と修正**

- Godotの型推論エラーを修正。インポートの終了コード0だけで成功とせず、ログの`SCRIPT ERROR`・`Parse Error`・`ERROR:`を確認した。
- 復元した投射物を型付き配列へ代入する箇所を`assign`に修正。
- 選択した施設の案内より光が優先されたため、地図からの目標選択を優先し、UI検査へ追加。
- 追加テストの変数名がGDScriptの予約語と衝突したので修正し、再実行。
- 旧模型の光の非表示対策を維持し、今回は実画面で光・敵・施設を確認した。

**結果と限界**

処理36項目＋UI5項目を通過。実画面では資金・座標・能力を与えずに光1つを回収し、旅先施設へアクセス、最深約306で燃料切れ帰還。8Cから4Cを使って航続Lv.1へ改修し、再起動でも保持された。遠方の建設・強化前後の同一敵・境界10000は状態注入による検査であり、通常の全域攻略ではない。

起点近くの光1つ、補給無料、失敗後の荷物保持、価格・在庫・90秒派遣などは全体をつなぐ仮仕様。具体値は設計図14章へ記載した。通常の長期試遊での逃走・経済・密度の体感、10000までの成長曲線はこれから。

画面とログは[検証記録](cloud-probe-validation.md)、通常操作は[模型の案内](cloud-probe-prototype-guide.md)。既存の局所模型と元リポジトリは変更せず、GitHubへもまだ配置していない。
